# INTERACT-001 — Constructive Virtual Grounds: interaction, not only observation

**Status:** executable bounded typed-data experiment. **Scope:** interpreted data operations, generated artifacts, causal edit/recovery; **not** pretrained full-model inference, unbounded natural-language comprehension or autonomous tool effects.

**Central distinction:** A catalogue says *which relations a source has*. A constructive Ground can **apply** qualified relations to that source, change its state under explicit caller authority, and **build** the requested result in a useful format. Rendering is a continuation of actual computation, not an annotation attached to a tensor inventory.

## Executable loop

```text
Actual observed source bytes (JSON typed records; external to state address)
             ↓ declared types + validated source SHA-256
   ConstructiveTableGround: versioned typed structure, actual rows
             ↓ intention selects operations and output columns
   state://vli/<fixed-width position>, computed BEFORE target value
             ↓ qualified arithmetic/filter/sort, fail on missing/wrong inputs
   derived records (data changes are committed only after validation)
             ↓ generated Markdown / CSV / canonical JSON / pure Python / text
   E-CPU exact byte Ground → VLD ResponseFormation DAG → selected views
             ↓ output + transcript receipts + pinned checkpoint/replay
     next intention, possibly operating on caller-authorized changed data
```

This reuses the **existing** `vli.response_state.ResponseFormation` for staged E-CPU/VLD rendering and `vli.ground` for digest conventions; it does **not** fork the response DAG, interpreter, or host authority machinery. The new module is `src/vli/constructive_data.py`.

### What it can build now

* **Derived data:** typed numeric operations (add, subtract, multiply, divide), ordered and equality predicates, sorted/limited selection, type-checked source fields. A division by zero or non-finite result refuses rather than publishing a fabricated state.
* **Actual artifact views:** a Markdown table from computed records, canonical JSON, UTF-8 CSV, an explanatory text statement, a byte-token rendering of that statement, and a generated **runnable Python function** that independently reconstructs the selected relation on matching source records. Text describes actual computed data; it is not a general LLM answer.
* **Mutable Ground:** a caller-authorized, type-preserving update modifies actual data records and creates a **different Ground digest**. Any subsequent query recomputes its results from the edited state. The same original state coordinate cannot be silently reused for altered values.
* **Evidence and recovery:** the source content is hashed; all transactions are tied to the current causal head. Checkpoint restoration replays each transformation **from original source bytes** under an externally supplied expected digest, including the E-CPU/VLD rendered observation digest where requested. Stale writes, changed source, altered plans and tampered receipts are refused.

The emitted Python source is synthesized from the *qualified mathematical query*, not generated by executing untrusted code. It is intentionally a pure function. Running it is optional for a user; independent test processes compare it to the direct Ground evaluator. This is a **small constructive algebra**, not arbitrary Python synthesis or general theorem-proving.

## Original large-model data, not reduced surrogates

The experiment [`examples/constructive_data_demo.py`](../examples/constructive_data_demo.py) loads VL-64's real archived **55,562,855,904-byte Qwen3.8-27B** and **510,286,023,000-byte DeepSeek-V4.1-Flash** *structural inventory evidence*, pinned to the exact immutable Git revision. It does **not** download, compress or claim to have computed those model weights.

From actual observed structure it constructs a derived per-model memory figure and average bytes per declared shard; writes Markdown, CSV, JSON, plain text and standalone Python; then performs one explicit action changing a **review workflow status** (not model mathematical state) and regenerates the output from the new Ground. It restores the checkpoint in a second instance to verify construction continuity. The E-CPU/VLD response DAG emits the constructed views through ordinary 64 KiB observation chunks.

This is meaningfully stronger than a static structural table because the values and code are **built**, the data can actually be changed, and future observations follow that change. It is **not** the stronger goal of realizing a complete Qwen/DeepSeek language answer by navigating their pretrained weights. The next step is to substitute the typed table's pure operators with **trained, qualified model operators and tokenizer relations**, preserving the same intent/coordinate/construction/renderer contracts and independent B2 numerical oracle.

### Reproduce

From VL-I, with pinned predecessor implementations installed:

```bash
python -m unittest discover -s tests -p test_constructive_data.py -v
python -m examples.constructive_data_demo \
  --upstream upstream/vl64 --out-dir artifacts/constructed-real-model-data
```

The [CI workflow](../.github/workflows/vli-constructive-data.yml) pins E-CPU, VLD and VL-64 at the same source revisions as existing successful experiments, runs both tests and full response-DAG rendering, then saves the actual generated artifacts. **Neither external model uses CPU inference** in this pass; it operates over previously observed structure.

## Falsifiable limits and next construction target

This experiment still requires an explicit typed operation plan or an **externally accepted** intent-selection mechanism. It cannot derive arbitrary free-text intent from a model header; it cannot generate trained model responses from metadata alone. It is also limited to bounded local table inputs; huge byte-oriented model data requires an external qualified operator/record-stream host rather than whole-file materialization. Its fixed-width coordinate is **not** a claim of constant-time neural computation.

The next construction frontier is to make structural model operators themselves targets of this mechanism: a Ground could select a typed kernel, qualify the required trained parameter coordinates, construct a live operator computation against a host, and render its checked numerical outputs into native tokens, code, conversation or authorized actions. Unverified operator behavior remains unresolved. The essential change is **from "this model contains an operation" to "perform this grounded operation, then build the result I asked for".**
